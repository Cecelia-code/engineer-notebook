# 为什么我需要一个技术博客

很多知识并不是“不会”，而是“当时会，过几周就散了”。  
博客最重要的价值不是展示，而是把零碎经验整理成之后还能复用的内容。

## 我希望这个站点承担什么角色

- 记录技术笔记，而不是只写完整教程。
- 保存踩坑过程，包括错误现象、排查路径和最终结论。
- 复盘项目决策，说明为什么当时这么做。
- 逐步积累自己的工具箱和方法论。

## 我的写作模板

平时可以按下面这个顺序写，能减少“开了文件不知道怎么下笔”的空白期：

```md
# 问题背景

# 现象与限制

# 解决过程

# 最终方案

# 还有哪些可以继续优化
```

## 这个博客为什么用 Markdown 驱动

Markdown 最大的好处是轻。  
内容是纯文本，迁移简单，版本管理也清楚，不会被某个平台绑住。

> 一篇好的技术笔记，不一定要长，但最好能回答“问题是什么、怎么解决、以后如何复用”。

## 下一步准备写什么

1. 前端工程化配置的最小可用方案。
2. 常用命令行工具的个人清单。
3. React 项目里一些常见的状态管理决策。
